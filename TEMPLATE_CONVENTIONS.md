# Template Conventions

Standardized structure shared by all Temlis Astro templates (Acelia, Vaultix, future).

Templates may diverge in **design language** (vanilla CSS vs Tailwind, etc.) and **animation language** (per-template GSAP eases, etc.), but every template MUST follow the conventions below.

## Tooling

| Aspect | Standard |
|---|---|
| Astro | `^6.1.7` or later |
| Node | `>=22.12.0` |
| TypeScript | `astro/tsconfigs/strict` |
| GSAP | npm OR CDN with `defer` — choose per-template, stay consistent within a project |
| Sitemap | `@astrojs/sitemap` enabled in `astro.config.mjs` |

## Conventions

### Components
- Flat structure in `src/components/`
- PascalCase filenames: `Hero.astro`, `Footer.astro`, `CtaSection.astro`
- For multi-pattern components, suffix the role: `*Section.astro`, `*Button.astro`, `*Canvas.astro`, `*Slider.astro`
- Each component is self-contained — props + scoped styles + (optional) inline `<script>`

### Styling
- Two approved approaches (template picks one, do not mix):
  - **Vanilla CSS** with fluid em-based scaling tokens (Acelia model)
  - **Tailwind v4** with `@theme` token block (Vaultix model)
- Global styles live in `src/styles/global.css`
- Design tokens always go in `global.css` — never inline hex in components

### Animations
- GSAP loaded ONE consistent way per template:
  - **npm import** model (Vaultix): `import { gsap } from 'gsap'` in components — tree-shaken, bundled
  - **CDN + defer** model (Acelia): `<script is:inline defer src="cdn.jsdelivr.net/.../gsap.min.js">` in `BaseLayout.astro`, all animation scripts use `is:inline` and read `gsap` from the global scope; component scripts guard with `if (typeof gsap === 'undefined') return`
- `gsap.registerPlugin(...)` called once in BaseLayout's animation entry script
- Respect `prefers-reduced-motion: reduce` — bail out of all animations when set
- Per-template custom eases live in `src/lib/eases.ts` (npm model) or inline (CDN model)

### Content
- All non-trivial data goes through Astro Content Collections (`src/content/<name>/*.md`)
- Schemas defined in `src/content.config.ts` using Zod
- Components consume collections via `getCollection()` — no hardcoded arrays where avoidable

### Deployment
- Every template has `.github/workflows/deploy.yml` + a root `wrangler.jsonc`
- Production branch: `main` → live URL (Workers auto-deploys on push to `main`)
- Target: **Cloudflare Workers (Static Assets)** — the worker just serves `dist/` (no `main`/entry-point)
- Workflow uses `cloudflare/wrangler-action@v3` (runs `wrangler deploy`) with `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` secrets
- `wrangler ^4` in devDependencies (wrangler-action@v3 installs v3, which rejects the no-`main` assets config)
- Worker naming: `temlis-<template-name>` in `wrangler.jsonc` (e.g., `temlis-acelia`, `temlis-vaultix`)

## Per-Template Differences (Allowed)

These are intentional and do NOT need to be unified:

| Aspect | Acelia | Vaultix |
|---|---|---|
| CSS framework | Vanilla CSS + fluid em scaling | Tailwind v4 + `@theme` tokens |
| Hosting target | Cloudflare Pages | Cloudflare Pages (Vercel adapter retained as option) |
| GSAP loading | CDN with `defer` + `is:inline` scripts | npm import + tree-shaking |
| Animation eases | `power4.out` mask reveals, character staggers | `vaultixStructure`, `vaultixReveal`, `vaultixDecor`, `vaultixExit` |
| Content shape | Wellness/consulting (cases, articles) | SaaS / product marketing (features, blog, team) |
| Custom canvas / 3D | none | Three.js `ParticleSphere`, halftone canvases |

The deployment target IS standardized (Cloudflare Workers for new templates; existing Pages sites stay on Pages). The CSS approach is not — pick the one that fits the project.
